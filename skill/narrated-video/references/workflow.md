# 制作流程与审批边界

## 新工程

1. 保存原始输入但不自动把 Markdown 标题或备注当作口播。
2. 让用户选择现有 Python、FFmpeg、TTS、Node/浏览器等实际需要的运行环境；通过 `preflight` 前不生成文案方案或素材。
3. 提交完整口播稿、主要改动和预计时长，等待明确批准。
4. 编写完整制作纲要和逐镜分镜：受众、平台、目标时长、叙事弧、节奏、视听方向、连续性锚点、素材策略、正负提示词、运镜、转场与 Demo 选择理由。
5. 分镜批准后只制作连续约 20–40 秒的代表性 Demo；观看关键帧、试听配音和混音并检查字幕安全区。
6. 记录用户真实 Demo 批准后再制作全片。

## 继续与局部修改

- 优先读取 `.narrated-video/state.json`、preflight 指纹和最近验证报告；有效选择和批准不重复询问。
- 文案或分句变化使 script、storyboard、Demo 批准失效。
- 完整分镜变化使 storyboard 批准失效；只有制作纲要、Demo 选段或 Demo 镜头内容变化才使 Demo 批准失效。
- Voice、字幕、输出、音乐、运行环境或 Demo 素材变化使 Demo 批准失效。
- 只替换非 Demo 素材时保留未受影响的 Demo 批准。

## 人声与音乐

- TTS 前让用户试听并选择音色；专名、多音字和发音代理必须用实际句子验证，字幕继续使用批准原文。
- 音乐先确认情绪、类型、能量、人声、平台和授权要求；提供至少三个可试听候选。用户选定前不下载、不写入工程、不渲染。
- 时间轴以处理后逐句 PCM 的真实帧数为准，不按字数估算。

## 交付

运行自动媒体检查，并人工检查首、中、尾、每个切镜点、字幕、转场和主观听感。说明实际检查范围；自动解码通过不代表内容、同步与审美全部合格。
